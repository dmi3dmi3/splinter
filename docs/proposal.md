# Splinter — предложение

Статус: черновик для обсуждения.

Splinter — self-hosted, local-first аналог Splitwise для компании друзей. Android-приложение, опциональный сервер синхронизации, публичный репозиторий, несколько авторов, AI-assisted разработка.

---

## 0. Проблема и решение

**Проблема.** В поездке компания платит вскладчину: кто-то за такси, кто-то за ужин, кто-то за всех купил билеты. Нужно в конце понять, кто кому сколько должен, и сделать это минимумом переводов. Splitwise это умеет, но данные лежат у третьей стороны, из России работает через раз, платные фичи ограничивают, а позиционный чек и общий кошелёк пары там не выразить.

**Решение.** Приложение, которое полностью работает офлайн на телефоне, а для синхронизации между телефонами использует свой сервер на дешёвом VPS, поднятый одним скриптом. Вся история — журнал событий, все балансы — вычисление из журнала, одинаковое на каждом телефоне бит в бит.

**Чем это не является.** Не сервис, не бизнес, не «убийца Splitwise». Инструмент для своей компании, открытый, чтобы им могли воспользоваться такие же компании.

---

## 1. Принципы

1. **Local-first.** Приложение полностью работает без сервера. Все расчёты — на клиенте. Сервер нужен только для синхронизации нескольких устройств.
2. **Self-host одним скриптом.** Сервер разворачивается на голый VPS командой в терминале, доступ по IP, без домена и внешних сервисов. Деплой из приложения по SSH — позже, как удобство.
3. **Append-only журнал.** Единственное, что хранится и синхронизируется, — события. Расходы, балансы, план переводов — проекции журнала, перестраиваемые в любой момент.
4. **Сервер не читает данные.** Сервер оперирует только конвертом события (группа, id, порядок). Содержимое — непрозрачный JSON. Дешёвая страховка под будущее E2E.
5. **Все могут всё.** Ролевой системы внутри поездки нет. Хост — это тот, кто поставил сервер; его права касаются только сервера.
6. **Поездки изолированы.** Одна поездка (группа) — замкнутый мир участников, расходов и курсов.
7. **Контракт первичен.** Каталог событий, правила расчётов, golden-фикстуры — первичны по отношению к коду. Все платформы обязаны давать одинаковый результат на одном журнале.
8. **Соразмерность.** Каждая фича — отдельный инкремент с фикстурой. Ничего «на вырост», кроме зарезервированных полей, которые стоят ноль.

## 2. Вне скоупа v1

- E2E-шифрование (архитектура подготовлена, реализация — когда появится хостинг для сторонних).
- iOS: будет отдельное нативное приложение на Swift, общий только контракт.
- Фото чеков и их парсинг.
- Ролевая система и подтверждение переводов получателем.
- Кошелёк на уровне операции (личный vs общий), временная привязка к кошельку.
- Веб-интерфейс.
- Деплой и управление сервером по SSH из приложения.
- Обновления в реальном времени на открытом экране (WebSocket / SSE).

## 3. Глоссарий

| Термин | Значение |
|---|---|
| **Поездка / группа** | Изолированный набор участников, расходов, переводов и настроек. |
| **Участник** | Человек в поездке. Создаётся как плейсхолдер (просто имя), к нему может быть привязано устройство. |
| **Устройство** | Установка приложения с ключевой парой. Одно устройство — не более одного участника в группе. |
| **Клейм** | Привязка устройства к участнику при входе по ссылке. |
| **Кошелёк** | Единица расчётов при взаимозачёте. По умолчанию у каждого участника свой неявный кошелёк; несколько участников могут делить общий. |
| **Сервер** | Инстанс Splinter Server на VPS. На одном сервере может быть много поездок. Устройство может быть подключено к нескольким серверам. |
| **Хост** | Устройство, зарегистрированное на сервере по хост-ссылке из скрипта установки. Создаёт группы на сервере, видит их список, управляет обновлением. |
| **Событие** | Неизменяемая запись в журнале группы. |
| **Проекция** | Состояние, вычисленное из событий (лента, балансы, план переводов). |
| **Порядок журнала** | Порядок событий на устройстве: синхронизированные — по `server_seq`, за ними неотправленные — по порядку создания. Единственный порядок, который используется в расчётах. |
| **Минорная единица** | Самая мелкая монета валюты: копейка, цент, тетри (1 лари = 100 тетри), фильс (1 динар = 1000 фильсов). У иены минорной единицы нет. Все суммы в контракте — целые в минорных единицах. |
| **Масштабированная единица** | Минорная единица × 1e6. Единица точных расчётов после конвертации курсом: «микрокопейка». |
| **Валюта отображения** | Локальная настройка устройства: в чём показывать балансы и план. На расчёты не влияет. |
| **Каноническая валюта** | Валюта, в которой считается план переводов, чтобы он совпал на всех устройствах. Выбирается детерминированно, пользователю не показывается. |

## 4. Архитектура

### 4.1 Обзор

```
┌──────────────────────┐       HTTPS (self-signed, pinned)        ┌──────────────────────┐
│  Android (Kotlin)    │ ◄──────────────────────────────────────► │  Splinter Server     │
│  Compose + Room      │   события, инвайты, регистрация          │  Python (FastAPI)    │
│  журнал + проекции   │                                          │  БД (см. §4.8)       │
└──────────────────────┘                                          │  docker compose      │
                                                                  └──────────▲───────────┘
                                                                             │ ssh
                                                       админ VPS ────────────┘
                                                       curl … | sudo bash   (deploy/install.sh)
```

- **Клиент** — источник истины для пользователя. Хранит полный журнал всех своих групп, считает все проекции, работает офлайн.
- **Сервер** — ретранслятор и точка встречи: принимает события, нумерует их, отдаёт по курсору, раздаёт инвайты. Не считает балансы, не валидирует содержимое.
- **Скрипт установки** — ставит сервер на VPS и печатает хост-ссылку, которую хост вставляет в приложение.
- Потеря сервера восстановима с любого клиента: клиент заливает свой журнал на новый сервер.

### 4.2 Событийная модель

Общий конверт события:

```json
{
  "event_id":       "uuid v7",
  "group_id":       "uuid",
  "device_id":      "uuid",
  "author_member":  "uuid | null",
  "created_at":     1789000000000,
  "type":           "ExpenseAdded",
  "schema_version": 1,
  "payload":        { },
  "signature":      "base64url | null",
  "server_seq":     123
}
```

`server_seq` проставляет сервер — монотонный счётчик внутри группы, он же курсор синхронизации и единственный источник порядка между устройствами. `created_at` — время по часам устройства, только для показа, на расчёты не влияет. `signature` — Ed25519 над каноническим JSON конверта без `signature` и `server_seq` (см. §4.6). Всё остальное создаёт клиент.

#### Каталог событий

**Группа**

| Тип | Payload | Примечание |
|---|---|---|
| `GroupCreated` | `name` | Первое событие журнала. |
| `GroupSettingChanged` | `key, value` | Одна настройка — одно событие. LWW на паре `(group, key)`. Ключи ниже. |

Ключи настроек:

| Ключ | Значение | Примечание |
|---|---|---|
| `name` | строка | |
| `closed` | bool | `true` — поездка в архиве: курсы и состав заморожены, новые расходы запрещены (UI). `false` — открыта заново. |
| `rate.<FROM>.<TO>` | int \| null | Курс пары валют в формате §4.4. `null` — курс удалён. |

История настроек видна целиком: каждое изменение — событие в журнале.

**Участники и кошельки**

| Тип | Payload | Примечание |
|---|---|---|
| `MemberAdded` | `member_id, name` | Плейсхолдер. Создать может любой. |
| `MemberClaimed` | `member_id, device_id, device_pubkey` | Устройство привязалось. |
| `MemberUnclaimed` | `member_id` | Вышел сам или отвязали. Плейсхолдер и его долги остаются. |
| `MemberArchived` | `member_id` | Скрыт из выбора. UI не даёт архивировать при ненулевом балансе, но событие само по себе валидно (защита от гонок). |
| `MemberProfileUpdated` | `member_id, name, payment_details` | Профиль единый на поездки: хранится на устройстве, при изменении эмитится во все группы, где устройство заклеймлено. |
| `WalletCreated` | `wallet_id, name` | Общий кошелёк. |
| `MemberWalletAssigned` | `member_id, wallet_id \| null` | `null` — вернуть в личный. **Ретроактивно на всю поездку** (см. §4.3). |

**Расходы и переводы**

| Тип | Payload | Примечание |
|---|---|---|
| `ExpenseAdded` | см. ниже | Трата. |
| `ExpenseUpdated` | полный payload расхода | Не дифф — полная замена. |
| `ExpenseDeleted` | `expense_id` | Возврат в магазине = удаление; частичный = правка. |
| `TransferRecorded` | `transfer_id, from_member, to_member, amount, currency, date, note?` | Перевод денег от участника участнику. Может как гасить долг, так и создавать его. Общая касса — это просто переводы держателю кассы. |
| `TransferUpdated` | полный payload | |
| `TransferDeleted` | `transfer_id` | |

Payload расхода:

```json
{
  "expense_id":  "uuid",
  "description": "Ужин в Кафе Литера",
  "date":        "2026-09-21",
  "currency":    "GEL",
  "payers": [
    { "member_id": "…", "amount": 24000, "wallet_id": null }
  ],
  "items": [
    {
      "item_id": "uuid",
      "name": "Хинкали",
      "amount": 8000,
      "shares": [
        { "member_id": "…", "amount": 4000, "wallet_id": null },
        { "member_id": "…", "amount": 4000, "wallet_id": null }
      ]
    }
  ],
  "extras": [
    {
      "name": "Сервисный сбор",
      "amount": 2400,
      "distribution": "equal | proportional",
      "shares": [ { "member_id": "…", "amount": 400 } ]
    }
  ]
}
```

Правила:
- Суммы — целые в минорных единицах валюты расхода.
- Простой расход «поровну» — один item с распределёнными долями.
- `extras` — дополнительные начисления к чеку (чаевые, сбор, скидка со знаком минус). В событие уходит результат распределения, не только правило.
- Инвариант: `sum(payers) == sum(items.shares) + sum(extras.shares)`.
- `wallet_id` в `payers[]` и `shares[]` — опциональное поле, зарезервировано под выбор кошелька на операцию. v1 не пишет.
- `date` — локальная дата строкой `YYYY-MM-DD`, без таймзоны. Редактируется пользователем, по умолчанию сегодня.

#### Версионирование

- `schema_version` на каждом событии.
- Клиент, встретивший неизвестный `type` или более новую версию, **игнорирует событие, не падает**, и показывает баннер «обновите приложение».
- Расширение payload — только добавлением опциональных полей.

### 4.3 Проекции

Все проекции строятся из журнала в порядке журнала, хранятся в Room как кэш и могут быть перестроены с нуля.

| Проекция | Из чего | Что содержит |
|---|---|---|
| **Настройки** | `GroupCreated`, `GroupSettingChanged` | Текущее значение каждого ключа по LWW. |
| **Курсы** | ключи `rate.*` | Таблица конвертации между всеми валютами поездки (§4.4). |
| **Участники** | `Member*`, `Wallet*` | Список, статус (плейсхолдер / заклеймлен / архивирован), профиль, кошелёк. |
| **Расходы и переводы** | `Expense*`, `Transfer*` | Текущая версия каждой сущности по LWW. |
| **Лента** | все события | Главный экран, правила отображения — §5.6. |
| **Нетто по валютам** | расходы, переводы, кошельки | `net[wallet][currency] = заплатил − доли + получил − отправил`, свёрнуто по кошелькам. |
| **Нетто в канонической** | нетто + курсы | По каждому блоку связанных валют, в масштабированных единицах канонической валюты блока. |
| **План переводов** | нетто в канонической | Результат алгоритма упрощения, по блоку. |

Конвертация в валюту отображения — не проекция, а функция показа поверх нетто и плана.

**Кошельки ретроактивны.** `net[wallet]` считается по текущему назначению участников в кошельки, для всей истории поездки. Назначение Марины в общий кошелёк с Митей в середине поездки сворачивает и все её прошлые доли. Это сознательное решение: «временная привязка» отклонена, иначе проекция зависела бы от порядка событий кошелька относительно расходов.

### 4.4 Правила расчётов (часть контракта)

Эти правила обязаны совпадать на всех платформах бит в бит и покрыты golden-тестами. **Вся арифметика — целочисленная.** Плавающая точка не используется нигде в контракте: дробные числа неточны (`0.1 + 0.2 ≠ 0.3`) и могут округлиться по-разному на разных платформах.

**Минорные единицы.** Таблица ISO 4217 в приложении: RUB/USD/EUR/GEL — 2 знака, JPY — 0, KWD — 3 и т. д. 24.00 GEL хранится как `2400`.

**Округление.** Единственный режим — *half away from zero*: `0.5 → 1`, `−0.5 → −1`. Применяется только в листьях (см. «Округление в листьях»), никогда внутри расчётов.

**Распределение суммы `T` по весам `w_1..w_n`** (метод наибольших остатков). Проблема: 100 ₽ на троих — по 33.33, в сумме 99.99, копейка повисла.
1. `W = Σ w_i`, `A = |T|`.
2. `base_i = A · w_i div W`, `rem_i = A · w_i mod W` — каждому округляем вниз.
3. `r = A − Σ base_i` — столько участников получают `+1`: с наибольшим `rem_i`; при равенстве — по порядку в списке долей. Для 100 на 3 это `34, 33, 33`.
4. Если `T < 0` — все доли отрицаются.

Сумма долей равна `T` по построению: остаток `r` — это ровно «всего минус сумма округлённых вниз», и раздаётся ровно он. Отсюда сумма нетто по всем участникам всегда ноль (инвариант 1).

Веса по режимам ввода:

| Режим | Веса |
|---|---|
| Поровну (по умолчанию) | все `1` |
| Точные суммы | распределения нет, суммы вводятся вручную, инвариант проверяется |
| Веса | целые, как введены |
| Проценты | базисные пункты (`12.5 % → 1250`), `Σ = 10000` |

Хранится результат распределения, не режим.

**Extras:** `equal` — сумма распределяется по правилу выше между всеми участниками расхода (у кого есть доля хоть в одном item), веса `1`; `proportional` — веса равны суммам долей участника по items.

**Курсы.** Курсы — пары, базовой валюты нет.
- Ключ `rate.<FROM>.<TO>`, значение — **масштабированных единиц `TO` за одну минорную единицу `FROM`**, то есть `minor(TO) / minor(FROM) × 1e6`. Для валют с одинаковым числом знаков это просто курс × 1e6: 1 GEL = 30.50 RUB → 1 тетри = 30.5 копейки → `rate.GEL.RUB = 30500000`. Для JPY и KWD число другое, пересчёт делает клиент при создании события; UI вводит и показывает привычное «1 GEL = 30.50 ₽».
- **Обратный курс** выводится: `rate(B→A) = round(1e12 / rate(A→B))`.
- **Через посредника:** `rate(A→C) = round(rate(A→B) · rate(B→C) / 1e6)`.
- **Правило выбора** курса `A→C` для проекции: прямая пара; иначе обратная от прямой `C→A`; иначе через одного посредника `B` — если посредников несколько, берётся наименьший по коду ISO. Длиннее одного посредника не ищем. Нет пути — валюты не связаны.
- Составной курс вычисляется **один раз как целое число** и потом применяется ко всем суммам. Так конвертация остаётся линейной, и сумма нетто по кошелькам после конвертации равна нулю точно (инвариант 2).

**Блоки и каноническая валюта.** Валюты поездки разбиваются на блоки: две валюты в одном блоке, если между ними есть курс по правилу выше. Каноническая валюта блока — наименьший код ISO в блоке. Нетто каждого кошелька конвертируется в масштабированные единицы канонической валюты: `net_canon[w] = Σ_c net[w][c] · rate(c→canon)`. **Без округления.** Валюта без единого курса — блок из одной валюты, каноническая — она сама.

**План переводов (упрощение долгов, всегда включено).** По каждому блоку, в масштабированных единицах его канонической валюты:
1. Кошельки с нетто > 0 — кредиторы, < 0 — должники.
2. Отсортировать обе группы по убыванию `|нетто|`, при равенстве — по `wallet_id`.
3. Перевод от крупнейшего должника крупнейшему кредитору на `min(|долг|, |кредит|)`, уменьшить обоих, обнулившегося убрать.
4. Повторять до пустоты.

Структура плана (кто кому) не зависит от того, в какой валюте его считать: конвертация умножает все нетто на одну константу и не меняет порядок сортировки. Поэтому план, посчитанный в канонической валюте, одинаков на всех устройствах, а показывается в любой.

**Округление в листьях.** Масштабированные единицы доходят до показа и только там округляются:
1. **Показ суммы** в валюте отображения `D`: `round(x · rate(canon→D) / 1e6)` минорных единиц `D`. Если `D` не в блоке — сумма показывается в канонической валюте блока.
2. **Сумма перевода в плане**: то же правило; переводы, округлившиеся в ноль, не показываются.
3. **Признак «рассчитались»**: `|net_canon| < 1e6`, то есть меньше одной минорной единицы канонической валюты. Считается в канонической, чтобы совпадать на всех устройствах. После реального перевода на 4 200,00 ₽ у участника остаётся хвост в доли копейки — он видит ноль.

Гарантии плана: ≤ n−1 переводов на блок; детерминизм на всех устройствах; в масштабированных единицах план применяется к нетто точно в ноль; после округления сумм переводов остаток по каждому кошельку меньше одной минорной единицы валюты показа. Переводы внутри одного кошелька невозможны.

`closed = true` замораживает курсы (UI) — защита от «ожившего» долга в 40 рублей через месяц после расчёта.

### 4.5 Синхронизация и порядок

**Порядок журнала.** Журнал устройства — упорядоченный список. Синхронизированные события идут в порядке `server_seq`; за ними — неотправленные, в порядке создания на устройстве. Это единственный порядок, который используют проекции. Без сервера (этап 1) журнал — просто порядок добавления, и ничего другого не нужно.

Почему не часы устройства: если Денис увидел правку Мити и поправил её ещё раз, его правка обязана победить. Она была создана после того, как правка Мити получила номер на сервере, и получит номер больше. Часы телефонов для этого не нужны, и их расхождение ни на что не влияет.

**Конфликты.** Единственная модель — **last-writer-wins по порядку журнала** на уровне сущности. Сущности: расход, перевод, участник, кошелёк, пара `(группа, ключ настройки)`. Побеждает то, что ниже в журнале. Для двух правок, сделанных офлайн независимо, это значит «побеждает тот, кто синхронизировался позже»; обе версии остаются в истории. Правило применяется единообразно, включая пару «удалил / отредактировал». Неотправленное на устройстве считается новее любого синхронизированного — ровно так оно и ляжет после отправки.

**Что делает сервер** (функционально; точный протокол — `contract/openapi.yaml` на этапе сервера):
- Отдаёт версию сервера и протокола без авторизации — чтобы приложение поняло, совместимо ли.
- Регистрирует устройство по хост-ссылке — устройство становится хостом.
- Хосту: создаёт группу, принимает начальный журнал, отдаёт список групп сервера (без имён — только id, размер журнала, дата последнего события).
- Участнику группы: создаёт и отзывает инвайты с TTL и лимитом использований.
- По инвайту: регистрирует устройство в группе, отдаёт название и список свободных плейсхолдеров, выдаёт токен устройства.
- Принимает пачку событий (идемпотентно по `event_id`), нумерует, возвращает номера. Отдаёт события после курсора порциями.

**Авторизация:** токен устройства, выданный при регистрации, привязан к устройству и к набору групп, в которые оно вошло.

**Цикл синка на клиенте** (на группу):
1. Отправить все неотправленные события в порядке журнала.
2. Запросить события после `last_server_seq`, дописать, обновить курсор.
3. Пересчитать затронутые проекции.

Триггеры: открытие приложения, создание события, «потянуть вниз», WorkManager раз в 15 минут. Обновления в реальном времени на открытом экране — позже (§6): WebSocket или Server-Sent Events, второе проще — это обычный HTTP-ответ, который не закрывается.

**Переезд и восстановление.** Заливка журнала на сервер идёт в порядке журнала, сервер нумерует по порядку получения — порядок сохраняется. То же при переезде на новый сервер. Импорт JSON в существующую поездку — только восстановление из бэкапа: слить два независимо изменённых журнала без сервера нельзя, порядок конфликтующих правок был бы не определён.

### 4.6 Идентичность и доступ

Три независимых механизма, которые нельзя схлопывать:

1. **Кто ты** — ключевая пара Ed25519 на устройстве, генерируется при первом запуске. Аккаунтов, email, паролей нет.
2. **Можно ли тебе в группу** — invite-токен на конкретную группу, с настраиваемыми TTL и числом использований.
3. **Что провода не слушают** — TLS с пиннингом (§4.7). Сертификат один на сервер, не на группу.

**Подпись событий.** Клиент подписывает каждое событие приватным ключом: Ed25519 над каноническим JSON (RFC 8785, JCS) конверта без `signature` и `server_seq`. В v1 ни сервер, ни клиенты подпись не проверяют — она только хранится. Смысл: события неизменяемы, дописать подписи к старым потом невозможно; на клиенте это десять строк.

**Клейм.** При входе по ссылке пользователь видит список незанятых плейсхолдеров группы и «Новый участник». Выбор → `MemberClaimed` + отправка своего профиля. Отвязать (`MemberUnclaimed`) может любой участник — это покрывает потерю телефона.

**Хост.** Скрипт установки печатает хост-ссылку `splinter://host?u=<host:port>&f=<sha256-b64url>&t=<host_token>`. Приложение по ней регистрирует устройство хостом. Только хост создаёт группы на сервере и видит их список. Внутри поездки хост ничем не отличается. Обновление сервера — тем же скриптом на VPS.

### 4.7 Транспортная безопасность

- При установке сервер генерирует self-signed сертификат (10 лет). Отпечаток SPKI (SHA-256) — «ключ с деплоя».
- Хост получает отпечаток из вывода скрипта в своей SSH-сессии → доверие бутстрапится через уже аутентифицированный канал.
- Отпечаток входит в хост-ссылку и в каждую invite-ссылку/QR. Клиент при первом подключении к серверу пинит его (`OkHttp CertificatePinner`); несовпадение = отказ.
- Домен и Let's Encrypt не нужны. Cleartext HTTP запрещён.
- Ротация сертификата — редкое хостовое действие, все получают новую ссылку.

**Формат invite-ссылки:** `splinter://join?u=<host:port>&f=<sha256-b64url>&t=<token>` — та же строка в QR. Токен привязан к одной группе.

### 4.8 Сервер

**Стек:** Python 3.12, FastAPI. Один или два контейнера в `docker compose` — зависит от выбора БД.

**Требования к хранилищу:** append-only таблица событий с монотонным `server_seq` внутри группы; уникальность `event_id`; выборка по `(group_id, server_seq > cursor)`; таблицы `groups`, `devices` (id, pubkey, токены — без имён), `invites`.

**БД — открытый вопрос (§9).** Два кандидата:
- **SQLite** в том же контейнере: один процесс, бэкап = копия файла, миграций почти нет. Достаточно для нагрузки «компания друзей».
- **PostgreSQL 16** отдельным контейнером: `pg_dump` кроном. Больше движущихся частей, зато привычнее.

Аргумент за простоту: полный журнал есть на каждом клиенте, восстановление = залить журнал на новый сервер, поэтому долговечность БД — не критичное требование.

**Установка (`deploy/install.sh`):** запускается на VPS root'ом или через sudo.
1. `/etc/os-release` → дистрибутив. **Полная автоматика: Ubuntu LTS, Debian.** Остальное — путь «Docker уже установлен», иначе понятная ошибка.
2. Если `docker` нет — `get.docker.com`. Проверить compose-plugin.
3. Открыть порт: `ufw` на Ubuntu/Debian; иначе сообщить.
4. Записать `/opt/splinter/{docker-compose.yml, .env}`, сгенерировать сертификат и хост-токен, `docker compose up -d`. Образы — с GHCR (зеркало под российские VPS), `amd64` + `arm64`.
5. Напечатать хост-ссылку и QR (`qrencode -t ANSI`, если есть).

Команды того же скрипта: `install.sh update` (`compose pull && up -d`, миграции на старте), `install.sh status`, `install.sh host-link` (напечатать ссылку ещё раз), `install.sh rotate-cert`. Файлы — в `/opt/splinter/`, контейнеры помечены `label=splinter`. Хост-креды в приложении не хранятся.

**Позже:** те же шаги из приложения по SSH, подключение к существующему серверу по `docker ps --filter label=splinter`. Скрипт остаётся источником истины, приложение его вызывает.

### 4.9 Пуши (опционально)

Чтобы отправить FCM-пуш, серверу нужен service-account ключ Firebase-проекта, к которому привязан APK. Раздать его каждому self-hosted серверу нельзя, а сама библиотека FCM проприетарна и закрывает дорогу в F-Droid.

**v1:** без пушей. WorkManager раз в 15 минут + синк при открытии и по «потянуть вниз».

**Позже:** пуш — только *poke* `{server, group_id}` без содержимого, приложение синкается само. Транспорт — **UnifiedPush**: без Google, совместим с F-Droid, сервер шлёт poke на URL, который выдал дистрибьютор на телефоне. На устройствах без дистрибьютора — polling.

### 4.10 Клиент

**Стек:** Kotlin, Jetpack Compose, Room, Hilt, OkHttp, kotlinx.serialization, WorkManager, ZXing (QR).

**Слои:**
- `contract` — модели событий, правила расчётов, алгоритмы проекций. Чистый Kotlin без Android-зависимостей, чтобы гонять golden-тесты на JVM без эмулятора. Это одна из реализаций контракта; iOS-клиент на Swift будет второй, и обе обязаны проходить одни и те же фикстуры.
- `data` — Room (журнал + кэш проекций), sync-клиент, ключи (Android Keystore).
- `ui` — Compose.

**Room:**

| Таблица | Назначение |
|---|---|
| `servers` | `url, fingerprint, device_token, is_host` |
| `groups` | `group_id, server_id?, my_member_id` |
| `events` | Сырой журнал в порядке журнала: `local_id (autoincrement), event_id, group_id, type, payload, server_seq?` |
| `sync_state` | `group_id, last_server_seq` |
| `settings`, `rates`, `members`, `wallets`, `expenses`, `transfers` | Кэш проекций, перестраиваемый. |
| `profile` | Локальный профиль устройства: имя, реквизиты, ключевая пара (Keystore), валюта отображения. |

**Аватарки** — детерминированно из `member_id` (цвет + инициалы), по одному алгоритму на всех устройствах, в событиях не хранятся. Кастомная аватарка — позже, как блоб в `MemberProfileUpdated` с лимитом payload 64 КБ.

**Дип-линки:** `splinter://join?…` (инвайт), `splinter://host?…` (хост-ссылка), `splinter://g/{group_id}/e/{expense_id}` (расход). Без https app links — домена нет.

### 4.11 Импорт из Splitwise

CSV-экспорт Splitwise даёт по каждому расходу дату, описание, сумму, валюту и нетто-изменение баланса каждого участника. Импортёр: участники → плейсхолдеры (с маппингом на существующих), расход → `ExpenseAdded` с одним item. Для расходов с одним плательщиком доли восстанавливаются точно (`share_i = −net_i`, плательщик — `cost − sum(others)`); для нескольких плательщиков — best-effort с пометкой в описании.

## 5. Логика работы приложения

### 5.1 Первый запуск

1. Генерируется ключевая пара Ed25519 и `device_id`, кладутся в Keystore.
2. Экран профиля: имя (обязательно), реквизиты для перевода (опционально, свободный текст: «СБП +7…», «IBAN …»), валюта отображения (по умолчанию — по локали).
3. Дальше — список поездок (пустой) с действиями: «Новая поездка», «Войти по ссылке», «Импорт» (JSON-бэкап или Splitwise CSV — создаёт новую поездку). Если приложение открыто по дип-линку — сразу соответствующий сценарий.

### 5.2 Навигация

```
Поездки ──► Поездка ──┬─ Лента (главный экран)
                      ├─ Балансы
                      ├─ Участники
                      └─ Настройки   (название, курсы, закрытие, экспорт)
                      [FAB: + Расход]   [меню: Записать перевод · Пригласить*]
```

`*` — «Пригласить» видна только у поездки на сервере. Поездка открывается на Ленте. Балансы и Участники — вкладки. Настройки — из меню.

### 5.3 Поездка

**Создание:** название, затем сразу экран «Кто едет?» — список плейсхолдеров, создатель уже в нём. Можно пропустить и добавить потом. → `GroupCreated`, `MemberAdded` на каждого, `MemberClaimed` + `MemberProfileUpdated` на создателя.

**Настройки:** название, таблица курсов, «Закрыть поездку» / «Открыть заново», «Экспорт журнала». Каждое поле — отдельное `GroupSettingChanged`.

**Курсы:** список валют, встречающихся в журнале, и связей между ними. Ввод пары вручную («1 GEL = 30.50 RUB») или «Подгрузить» (источник — §9). Обновление уже заданного курса — с предупреждением «балансы могут измениться». Каждая пара — своё событие `rate.<FROM>.<TO>`. Валюты, не связанные с остальными, помечены.

**Закрытие:** `closed = true`. UI прячет «+ Расход», блокирует правку курсов и состава, поездка уходит в раздел «Архив». «Открыть заново» — с предупреждением, `closed = false`.

**Пригласить:** экран инвайта: ссылка + QR, TTL (по умолчанию 7 дней), число использований (по умолчанию — число свободных плейсхолдеров, если их нет — 10). Экран настроек ссылки — обсудить отдельно.

**Экспорт/импорт:** JSON-файл с полным журналом группы в порядке журнала (`{version, events: [...]}`). Импорт из списка поездок создаёт поездку; импорт в существующую — только восстановление, дописывает недостающие события по `event_id`.

### 5.4 Расход

Форма создания, сверху вниз:

1. **Сумма** — поле-калькулятор: `120+80*2` считается на лету. Рядом валюта: по умолчанию валюта последней операции, в быстром доступе — недавние валюты поездки, дальше полный список.
2. **Описание.**
3. **Кто платил** — по умолчанию «я». Тап — выбор одного или нескольких с суммами; суммы нескольких плательщиков должны сходиться к итогу.
4. **Как делить** — переключатель режимов:
   - *Поровну* (по умолчанию): чекбоксы участников, все включены.
   - *Точные суммы*: поле у каждого, остаток показан.
   - *Веса*: целое у каждого.
   - *Проценты*: с одним знаком после запятой.
   - *По позициям*: список позиций «название, сумма, кто», каждая — поровну между выбранными; ниже — extras «название, сумма (можно отрицательную), equal/proportional».
5. **Дата** — сегодня, тап меняет.
6. **Сохранить** → `ExpenseAdded` с посчитанными долями. Внизу формы всегда виден результат: «Айрат 40.00 · Никита 40.00 · …», чтобы остаток округления был виден до сохранения.

Правка открывает ту же форму, заполненную из текущей версии → `ExpenseUpdated` с полным payload. Удаление — с подтверждением → `ExpenseDeleted`.

Расход в закрытой поездке открывается только на чтение.

### 5.5 Балансы

Всё показывается в валюте отображения устройства; блок валют, до которого нет курса из валюты отображения, показывается в своей канонической валюте с пометкой «нет курса к …». Экран из трёх уровней, сверху вниз:

1. **Мой итог.** «Вы должны 4 200 ₽» / «Вам должны …» / «Вы рассчитались». Если в поездке несколько несвязанных блоков валют — по строке на блок и баннер «GEL и USD не связаны курсом: задать».
2. **План переводов.** Строки «кто → кому сумма», мои — наверху. У моей строки-долга кнопка **«Погасить»**: форма перевода, предзаполненная от/кому/сумма/валюта, ниже — реквизиты получателя из его профиля. Подтверждение → `TransferRecorded`. У чужих строк — просто информация. Сумма перевода округлена в лист; строки, округлившиеся в ноль, не показываются.
3. **Нетто по кошелькам.** Список кошельков с нетто. Общий кошелёк раскрывается на участников. Участник раскрывается на список расходов и переводов, из которых сложилось: «Ужин −800 · Такси −200 · Перевод Мите +1 000». Это ответ на «из чего сложилось».

**«Записать перевод»** из меню — та же форма, пустая, валюта — как в расходе (последняя + недавние). Частичное погашение и переплата легальны: это просто перевод, проекция пересчитает.

### 5.6 Лента

Правила отображения — часть контракта, потому что от них зависит, что пользователь считает «порядком событий».

- **Что показывается строкой:** расходы, переводы. Порядок — по `date` (убывание), внутри одной даты — по порядку журнала (убывание). Ключ сортировки берётся из текущей версии сущности. Суммы — в валюте операции, рядом мелко — в валюте отображения, если они различаются.
- **Правки:** строка расхода/перевода показывает текущую версию. Тап раскрывает историю версий по порядку журнала, каждая — как дифф с предыдущей: «Денис изменил: участники −Валя; сумма 250 → 240». Удалённая сущность — строка «удалено» серым, с историей.
- **Служебные события** (`Member*`, `Wallet*`, `GroupSettingChanged`) — свёрнуты в одну строку «3 служебных события» между датами, раскрываются фильтром. Подряд идущие `GroupSettingChanged` одного устройства — одна строка: «Никита обновил курсы GEL→RUB, USD→RUB».
- **Неизвестные события** — не показываются, но считаются: баннер «2 события не распознаны — обновите приложение».
- **Синк:** индикатор наверху: «3 события не отправлены» / «синхронизировано» / «сервер недоступен». Тап или «потянуть вниз» — принудительный синк.

### 5.7 Участники

Список: аватарка, имя, статус (плейсхолдер / привязан / архивирован), кошелёк, реквизиты. Действия:
- «Добавить участника» → `MemberAdded`.
- На участнике: «Отвязать устройство» (если привязан), «Архивировать» (только при `|net_canon| < 1e6` во всех блоках; иначе «сначала закройте долг»), «Кошелёк: личный / …».
- «Создать общий кошелёк» → `WalletCreated`, потом назначение участников → `MemberWalletAssigned`. Предупреждение при назначении: «действует на всю поездку».
- «Выйти из поездки» на себе → `MemberUnclaimed`, поездка остаётся локально в режиме «только чтение, не синкается» до удаления пользователем.

### 5.8 Вход по ссылке

1. Открыт `splinter://join?…`. Приложение проверяет отпечаток при первом подключении к серверу, запоминает сервер.
2. По инвайт-токену получает название группы и список незанятых плейсхолдеров.
3. Экран «Поездка Грузия. Кто ты?» — плейсхолдеры + «Новый участник».
4. Выбор → регистрация в группе, токен устройства сохранён, журнал скачан, эмитятся `MemberClaimed` (+ `MemberAdded` для нового) и `MemberProfileUpdated`.
5. Если у устройства уже есть участник в этой группе — ссылка просто открывает поездку.
6. Если группа на сервере пустая (хост создал её под чужую локальную поездку), приложение предлагает залить в неё локальную поездку — см. С13.

### 5.9 Сервер и хост

- **«Подключить сервер»** в списке поездок → вставить/сканировать хост-ссылку → устройство зарегистрировано хостом, сервер в списке с пометкой «хост».
- **Хост видит** список групп сервера (без имён — только id, размер, дата), может «Подключить» группу: скачать журнал, затем клеймить себя. Локальную поездку хост может «Отправить на сервер»: создаёт группу и заливает журнал.
- **Хост создаёт пустую группу** под чужую локальную поездку и делится инвайтом; владелец поездки входит по нему и заливает свой журнал (С13).
- **Любой участник** поездки на сервере может создавать инвайты в неё.
- **Обновление сервера** — на VPS: `install.sh update`. Приложение при несовместимой версии протокола показывает: «сервер 0.4, нужен ≥ 0.6, обновите на VPS».

### 5.10 Синхронизация с точки зрения пользователя

- Создал событие → оно сразу в проекциях, помечено «не отправлено» → уходит при ближайшем синке.
- Пришло чужое → проекции пересчитаны, лента обновилась.
- Конфликт — не диалог. Проигравшая версия видна в истории строки, победившая — в ленте. Пользователь правит ещё раз, если не согласен.
- Офлайн неделю — ничего не ломается: при первом синке всё уходит и приходит, сервер расставляет порядок.

## 8. Репозиторий и процесс

**Монорепозиторий** `splinter` с явным разделением:

```
splinter/
├── contract/          # источник истины: schema/, spec/, golden/, openapi.yaml
├── android/           # Gradle-проект: :contract (чистый Kotlin), :data, :ui, :app
├── server/            # Python: splinter_server/, tests/, Dockerfile
├── deploy/            # install.sh, docker-compose.yml, README
├── docs/              # это предложение, adr/
├── CLAUDE.md          # = AGENTS.md: где контракт, что нельзя ломать, как гонять golden
└── LICENSE
```

- В `contract/`: JSON Schema событий, спецификация расчётов и порядка текстом, golden-фикстуры (`log.json → expected.json`), OpenAPI протокола. Контракт фиксируется этими тремя вещами; реализации на любом языке проверяются фикстурами. Kotlin-модели проверяются против схемы в CI. Сервер валидирует только конверт.
- `CLAUDE.md` в корне: где лежит контракт, какие инварианты нельзя ломать, как гонять golden-тесты. ADR в `docs/adr/` на каждое решение из этого документа.
- CI: golden-тесты `android/contract` и `server` на каждый PR; для сервера — интеграционный тест синка двух клиентов.
- **Лицензия** — AGPL-3.0 (FLOSS, подходит F-Droid; форки сервера обязаны открывать код).

**Распространение APK:**
1. **GitHub Releases** с самого начала. Ключ подписи — у одного мейнтейнера, не в репо.
2. **F-Droid** — когда приложение станет цельным (ориентир: конец этапа 2). F-Droid собирает из исходников сам и требует отсутствия проприетарных зависимостей — у нас их не будет (пуши только через UnifiedPush).

## 10. Юзер-сценарии

Компания: **Митя** (хост), **Марина** (общий кошелёк с Митей), **Айрат**, **Валя**, **Никита**, **Денис**. Поездка «Грузия». Митя и Марина смотрят балансы в рублях, Айрат — в лари.

### С1. Первая поездка без сервера *(1a)*
Митя создаёт «Грузия», на экране «Кто едет?» вводит: Марина, Айрат, Валя, Никита, Денис; себя приложение добавило само. Вбивает первый расход: «Такси из аэропорта», 2 400 ₽, платил Митя, поровну на всех. Лента показывает одну строку, балансы — пять должников Мите по 400 ₽. Сервера нет.

### С2. Чек по позициям с доп. начислениями *(1c)*
Ужин. Марина вводит позиции: хинкали 80 GEL — Айрат и Никита; вино 120 GEL — все, кроме Марины; чача 30 GEL — Митя. Добавляет extra «сервис 10 %» = 23 GEL пропорционально, скидка по акции −20 GEL пропорционально. Платила Марина. Внизу формы до сохранения видно: доли посчитаны, остаток округления в 1 тетри ушёл первому в списке. Одно событие `ExpenseAdded`.

### С3. Балансы и «Погасить» *(1a)*
Через неделю Айрат открывает «Балансы»: «Вы должны 140 GEL» — он смотрит в лари, курс GEL→RUB задан. План: «Айрат → Митя & Марина 140 GEL» — хотя часть ужинов оплачивала Валя, упрощение свело всё к одному переводу. Айрат раскрывает строку, видит расходы, из которых сложилась сумма. Нажимает «Погасить»: форма с предзаполненными от/кому/сумма, валюту меняет на RUB — 4 200 ₽, ниже — реквизиты Мити для СБП. Переводит в банке, подтверждает. `TransferRecorded` на 4 200 ₽. В масштабированных единицах у Айрата остался хвост в доли копейки от конвертации; экран показывает «Вы рассчитались». Митя видит тот же перевод как «+4 200 ₽».

### С4. Произвольный перевод *(1a)*
Никита занял у Дениса 3 000 ₽ наличными вне всяких чеков. Денис нажимает «Записать перевод», выбирает Никита → Денис… останавливается: деньги шли от Дениса к Никите. Записывает Денис → Никита 3 000 ₽. У Никиты появился долг Денису, которого не было в расходах. Общая касса работает так же: все скидываются Мите переводами, он платит из этого.

### С5. Общий кошелёк *(1d)*
Марина создаёт кошелёк «Митя & Марина» и назначает обоих; приложение предупреждает, что это действует на всю поездку. В расходе на шестерых у Мити и Марины по 1/6 каждому. На экране балансов — одна строка «Митя & Марина», нетто 1/3, раскрывается на двоих. План переводов никогда не предлагает перевод между ними. Кто из двоих платил картой — не важно.

### С6. Установка сервера *(этап 2)*
Митя купил VPS на Ubuntu. Заходит по SSH, запускает `curl -fsSL …/install.sh | sudo bash`. Скрипт: Ubuntu 24.04, Docker нет, ставит, открывает порт, поднимает compose, печатает хост-ссылку и QR. Митя сканирует QR приложением — устройство зарегистрировано хостом. Выбирает «Грузия» → «Отправить на сервер» → группа создана, журнал уехал в порядке журнала. «Пригласить» → ссылка и QR: TTL 7 дней, 5 использований — по числу свободных плейсхолдеров.

### С7. Вход по ссылке *(этап 2)*
Валя открывает ссылку — приложения нет, попадает в GitHub Releases, ставит APK, открывает ссылку снова. «Поездка Грузия. Кто ты? Марина · Айрат · Валя · Никита · Денис · Новый участник». Выбирает Валю, приложение отправляет её профиль и тянет журнал. Денис пришёл позже, чем ожидалось, и его никто не завёл — он выбирает «Новый участник», вводит имя, `MemberAdded` + `MemberClaimed`.

### С8. Офлайн параллельно *(этап 2)*
В горах без связи Никита записывает бензин, Айрат — обед. Вечером в отеле оба синкаются: каждый отправляет своё, получает чужое, сервер нумерует, балансы у всех совпадают. Конфликтов нет — это разные сущности.

### С9. Конфликт правки *(этап 2)*
Митя и Денис офлайн правят один ужин: Митя меняет сумму 240 → 250, Денис убирает Валю из участников. Денис синхронизировался в 19:00, Митя в 20:00 — правка Мити встала ниже в журнале и победила: в ленте текущая версия — 250 с Валей. Денис раскрывает историю: «Денис изменил: участники −Валя», затем «Митя изменил: участники +Валя; сумма 240 → 250» — и правит ещё раз, если нужно. Обе версии в истории.

### С10. Курсы и мультивалюта *(1e)*
Часть расходов в GEL, перелёты в RUB, один ужин в USD. Балансы у Мити показывают: «GEL и USD не связаны курсом» отдельными блоками. Валя нажимает «Подгрузить курсы» — приложение тянет GEL→RUB и USD→RUB на сегодня, два события `GroupSettingChanged`, все три валюты в одном блоке, план один. Айрат видит тот же план в лари: приложение вывело курс RUB→GEL как обратный. Через две недели Никита нажимает «Обновить курсы», видит предупреждение «балансы могут измениться», соглашается — у всех сдвинулось на десятки рублей, и это видно в ленте одной строкой «Никита обновил курсы GEL→RUB, USD→RUB».

### С11. Потеря телефона *(этап 2)*
Никита утопил телефон. Новый телефон, ссылка от Мити, в списке «Никита» помечен как занятый. Любой участник (Митя) нажимает «Отвязать Никиту» → `MemberUnclaimed`. Никита выбирает себя, `MemberClaimed`, все его долги на месте, история — тоже.

### С12. Переустановка приложения и обновление сервера *(этап 2)*
Митя снёс приложение. Ставит заново, «Подключить сервер»: заходит на VPS, `install.sh host-link`, сканирует QR. Приложение видит сервер 0.4 против своего 0.6, говорит «обновите сервер». Митя запускает `install.sh update`, миграции на старте. Приложение показывает две группы на сервере, Митя подключает «Грузию», тянет журнал, заклеймливает себя.

### С13. Две поездки на одном сервере *(этап 2)*
Валя создаёт «Байкал» локально. Просит Митю — тот как хост создаёт на сервере пустую группу и шлёт Вале инвайт. Валя открывает ссылку, приложение видит пустую группу и предлагает залить в неё локальную поездку: журнал «Байкала» уезжает в порядке журнала. Дальше Валя сама приглашает остальных. В «Байкале» нет Мити. Митя как хост видит на сервере обе группы, подключён к одной. Балансы «Грузии» и «Байкала» не пересекаются.

### С14. Выход и архивирование *(1f, этап 2)*
Денис вернулся домой, долги закрыл, «Выйти из поездки» → устройство отвязано, плейсхолдер и история остались. Марина хочет убрать «Гостя», у которого висит 200 ₽, — приложение говорит «сначала закройте долг». После перевода «Гость» архивируется и исчезает из выбора участников, но остаётся в истории.

### С15. Возврат в магазине *(1a)*
Айрат вернул куртку, за которую платил на всех. Удаляет расход — `ExpenseDeleted`, балансы пересчитались. Вернули половину — правит сумму.

### С16. Без пушей и без Google *(этап 2)*
У Никиты Huawei без Google-сервисов. Он открывает приложение — синк при старте. Пока закрыто — WorkManager раз в 15 минут. Ничего не теряется, просто узнаёт не мгновенно.

### С17. Импорт из Splitwise *(1g)*
Валя выгружает CSV из старой группы Splitwise, в списке поездок нажимает «Импорт». Приложение показывает найденных участников и предлагает сопоставить с плейсхолдерами; расходы ложатся в новую поездку как `ExpenseAdded` с пометкой «импорт из Splitwise». Балансы совпадают с тем, что показывал Splitwise.

### С18. Закрытие и повторное открытие *(1f)*
Все рассчитались. Митя нажимает «Закрыть поездку» → `closed = true`. Курсы и состав заморожены, новые расходы нельзя, поездка уходит в архив. Через месяц Валя вспоминает забытый чек: «Открыть заново» с предупреждением → `closed = false`, добавляет расход, закрывает снова. В ленте оба переключения видны.

### С19. Конфликт настроек *(этап 2)*
Офлайн: Валя задаёт курс GEL→RUB, Никита в тот же час — курс USD→RUB, а Митя переименовывает поездку в «Грузия 2026». После синка выжили все три изменения: LWW идёт по паре `(группа, ключ)`, а не по «настройкам целиком».

## 11. Инварианты и golden-тесты

Фикстуры `contract/golden/<case>/{log.json, expected.json}`, прогоняются на каждой платформе. `log.json` — журнал в порядке журнала. `expected.json` содержит настройки, курсы, участников, нетто по валютам, блоки с канонической валютой и нетто в ней, план переводов (в масштабированных единицах и округлённый в указанной валюте отображения) и порядок ленты.

1. Сумма нетто по каждой валюте равна нулю на любом журнале.
2. Сумма нетто в канонической валюте по кошелькам каждого блока равна нулю точно (в масштабированных единицах) на любом журнале с любыми курсами.
3. План переводов в масштабированных единицах, применённый к нетто блока, даёт нули по всем кошелькам; после округления сумм переводов в любую валюту показа остаток по каждому кошельку меньше одной её минорной единицы.
4. Проекции — функция порядка журнала: один и тот же журнал, разбитый на любые порции синхронизации, даёт идентичные проекции; журнал, залитый на сервер и скачанный обратно, — тоже.
5. Общий кошелёк из двух участников с долями 1/6 + 1/6 → нетто 1/3 в плане; перевод между ними не генерируется; назначение в кошелёк после расходов даёт тот же результат, что до.
6. Распределение 100 на 3 поровну → `34, 33, 33` в порядке участников; 1000 JPY на 3 → `334, 333, 333`; 1.000 KWD на 3 → `334, 333, 333` в фильсах; −100 на 3 → `−34, −33, −33`; 100 по весам 1:2 → `33, 67`.
7. Extras `equal` и `proportional` дают ожидаемые доли на эталонном чеке из С2.
8. Изменение курса меняет нетто в канонической, но не нетто по валютам. Смена валюты отображения не меняет ни структуру плана, ни признак «рассчитались».
9. Курсы: обратный и составной через посредника считаются по формулам §4.4; при двух посредниках берётся наименьший по коду; при отсутствии пути валюта образует отдельный блок; каноническая валюта блока — наименьший код.
10. LWW: при двух `ExpenseUpdated` в проекции — версия, стоящая ниже в журнале; неотправленное событие побеждает синхронизированное.
11. LWW по настройкам: `rate.GEL.RUB`, `rate.USD.RUB` и `name` из трёх источников (С19) выживают все.
12. Неизвестный тип события пропускается, остальные применяются; счётчик пропущенных равен ожидаемому.
13. Импорт эталонного Splitwise-CSV даёт балансы, совпадающие с эталоном.
14. Экспорт → импорт журнала даёт идентичные проекции.
