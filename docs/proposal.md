# Splinter — предложение (proposal)

Статус: **v0.2, черновик для обсуждения** · 21 сентября 2026
Предыдущая версия: v0.1 (дизайн-документ). Список изменений — в конце.

Splinter — self-hosted, local-first аналог Splitwise для компании друзей. Android-приложение, опциональный сервер синхронизации, публичный репозиторий, несколько авторов, AI-assisted разработка.

---

## 0. Проблема и решение

**Проблема.** В поездке компания платит вскладчину: кто-то за такси, кто-то за ужин, кто-то за всех купил билеты. Нужно в конце понять, кто кому сколько должен, и сделать это минимумом переводов. Splitwise это умеет, но данные лежат у третьей стороны, из России работает через раз, платные фичи ограничивают, а позиционный чек и общий кошелёк пары там не выразить.

**Решение.** Приложение, которое полностью работает офлайн на телефоне, а для синхронизации между телефонами использует свой сервер на дешёвом VPS, поднятый одним скриптом. Вся история — журнал событий, все балансы — вычисление из журнала, одинаковое на каждом телефоне бит в бит.

**Чем это не является.** Не сервис, не бизнес, не «убийца Splitwise». Инструмент для своей компании, открытый, чтобы им могли воспользоваться такие же компании.

---

## 1. Принципы

1. **Local-first.** Приложение полностью работает без сервера. Все расчёты — на клиенте. Сервер нужен только для синхронизации нескольких устройств.
2. **Self-host одним скриптом.** Сервер разворачивается на голый VPS командой в терминале, доступ по IP, без домена и внешних сервисов. Деплой из приложения по SSH — позже, как удобство.
3. **Append-only журнал.** Единственное, что хранится и синхронизируется, — события. Расходы, балансы, план переводов — проекции журнала, перестраиваемые в любой момент.
4. **Сервер не читает данные.** Сервер оперирует только конвертом события (группа, id, порядок). Содержимое — непрозрачный JSON. Дешёвая страховка под будущее E2E.
5. **Все могут всё.** Ролевой системы внутри поездки нет. Хост — это тот, кто поставил сервер; его права касаются только сервера.
6. **Поездки изолированы.** Одна поездка (группа) — замкнутый мир участников, расходов и курсов.
7. **Контракт первичен.** Каталог событий, правила расчётов, golden-фикстуры — первичны по отношению к коду. Все платформы обязаны давать одинаковый результат на одном журнале.
8. **Соразмерность.** Каждая фича — отдельный инкремент с фикстурой. Ничего «на вырост», кроме зарезервированных полей, которые стоят ноль.

## 2. Вне скоупа v1

- E2E-шифрование (архитектура подготовлена, реализация — когда появится хостинг для сторонних).
- iOS (см. §4.10: контракт держится чистым Kotlin, чтобы позже стать Kotlin Multiplatform).
- Фото чеков и их парсинг.
- Ролевая система и подтверждение переводов получателем.
- Кошелёк на уровне операции (личный vs общий), временная привязка к кошельку.
- Веб-интерфейс.
- Деплой и управление сервером по SSH из приложения (этап 3).

## 3. Глоссарий

| Термин | Значение |
|---|---|
| **Поездка / группа** | Изолированный набор участников, расходов, переводов и настроек. |
| **Участник** | Человек в поездке. Создаётся как плейсхолдер (просто имя), к нему может быть привязано устройство. |
| **Устройство** | Установка приложения с ключевой парой. Одно устройство — не более одного участника в группе. |
| **Клейм** | Привязка устройства к участнику при входе по ссылке. |
| **Кошелёк** | Единица расчётов при взаимозачёте. По умолчанию у каждого участника свой неявный кошелёк; несколько участников могут делить общий. |
| **Сервер** | Инстанс Splinter Server на VPS. На одном сервере может быть много поездок. Устройство может быть подключено к нескольким серверам. |
| **Хост** | Устройство, зарегистрированное на сервере по хост-ссылке из скрипта установки. Видит список групп сервера, управляет обновлением. |
| **Событие** | Неизменяемая запись в журнале группы. |
| **Проекция** | Состояние, вычисленное из событий (лента, балансы, план переводов). |
| **HLC** | Hybrid Logical Clock — метка времени для упорядочивания событий между устройствами. |
| **Минорная единица** | Копейка, цент, тетри, фильс. Все суммы в контракте — целые в минорных единицах. |
| **Масштабированная единица** | Минорная единица базовой валюты × 1e6. Единица точных расчётов после конвертации курсом. |

## 4. Архитектура

### 4.1 Обзор

```
┌──────────────────────┐       HTTPS (self-signed, pinned)        ┌──────────────────────┐
│  Android (Kotlin)    │ ◄──────────────────────────────────────► │  Splinter Server     │
│  Compose + Room      │   POST/GET events, WS stream, invites    │  Python (FastAPI)    │
│  журнал + проекции   │                                          │  БД (см. §4.8)       │
└──────────────────────┘                                          │  docker compose      │
                                                                  └──────────▲───────────┘
                                                                             │ ssh
                                                       админ VPS ────────────┘
                                                       curl … | sudo bash   (deploy/install.sh)
```

- **Клиент** — источник истины для пользователя. Хранит полный журнал всех своих групп, считает все проекции, работает офлайн.
- **Сервер** — ретранслятор и точка встречи: принимает события, нумерует их, отдаёт по курсору, раздаёт инвайты. Не считает балансы, не валидирует содержимое.
- **Скрипт установки** — ставит сервер на VPS и печатает хост-ссылку, которую хост вставляет в приложение.
- Потеря сервера восстановима с любого клиента: клиент заливает свой журнал на новый сервер.

### 4.2 Событийная модель

Общий конверт события:

```json
{
  "event_id":       "uuid v7",
  "group_id":       "uuid",
  "device_id":      "uuid",
  "author_member":  "uuid | null",
  "hlc":            "0000018a3f2c1e80-0003-a1b2c3d4",
  "type":           "ExpenseAdded",
  "schema_version": 1,
  "payload":        { },
  "signature":      "base64url | null",
  "server_seq":     123
}
```

`server_seq` проставляет сервер — монотонный счётчик внутри группы, он же курсор синхронизации. `signature` — Ed25519 над каноническим JSON конверта без `signature` и `server_seq` (см. §4.6). Всё остальное создаёт клиент.

#### Каталог событий

**Группа**

| Тип | Payload | Примечание |
|---|---|---|
| `GroupCreated` | `name, base_currency` | Первое событие журнала. |
| `GroupSettingChanged` | `key, value` | Одна настройка — одно событие. LWW на паре `(group, key)`. Ключи ниже. |

Ключи настроек:

| Ключ | Значение | Примечание |
|---|---|---|
| `name` | строка | |
| `base_currency` | ISO 4217 | Смена базовой валюты обнуляет курсы (см. §9). |
| `closed` | bool | `true` — поездка в архиве: курсы и состав заморожены, новые расходы запрещены (UI). `false` — открыта заново. |
| `rate.<CUR>` | int \| null | Курс валюты `CUR` к базовой в формате §4.4. `null` — курс удалён. |

История настроек видна целиком: каждое изменение — событие в журнале.

**Участники и кошельки**

| Тип | Payload | Примечание |
|---|---|---|
| `MemberAdded` | `member_id, name` | Плейсхолдер. Создать может любой. |
| `MemberClaimed` | `member_id, device_id, device_pubkey` | Устройство привязалось. |
| `MemberUnclaimed` | `member_id` | Вышел сам или отвязали. Плейсхолдер и его долги остаются. |
| `MemberArchived` | `member_id` | Скрыт из выбора. UI не даёт архивировать при ненулевом балансе, но событие само по себе валидно (защита от гонок). |
| `MemberProfileUpdated` | `member_id, name, payment_details` | Профиль единый на поездки: хранится на устройстве, при изменении эмитится во все группы, где устройство заклеймлено. |
| `WalletCreated` | `wallet_id, name` | Общий кошелёк. |
| `MemberWalletAssigned` | `member_id, wallet_id \| null` | `null` — вернуть в личный. **Ретроактивно на всю поездку** (см. §4.3). |

**Расходы и переводы**

| Тип | Payload | Примечание |
|---|---|---|
| `ExpenseAdded` | см. ниже | |
| `ExpenseUpdated` | полный payload расхода | Не дифф — полная замена. |
| `ExpenseDeleted` | `expense_id` | Возврат в магазине = удаление; частичный = правка. |
| `SettlementRecorded` | `settlement_id, from_member, to_member, amount, currency, date, note?` | Перевод денег. Общая касса — это просто переводы держателю кассы. |
| `SettlementUpdated` | полный payload | |
| `SettlementDeleted` | `settlement_id` | |

Payload расхода:

```json
{
  "expense_id":  "uuid",
  "description": "Ужин в Кафе Литера",
  "date":        "2026-09-21",
  "currency":    "GEL",
  "payers": [
    { "member_id": "…", "amount": 24000, "wallet_id": null }
  ],
  "items": [
    {
      "item_id": "uuid",
      "name": "Хинкали",
      "amount": 8000,
      "shares": [
        { "member_id": "…", "amount": 4000, "wallet_id": null },
        { "member_id": "…", "amount": 4000, "wallet_id": null }
      ]
    }
  ],
  "extras": [
    {
      "name": "Сервисный сбор",
      "amount": 2400,
      "distribution": "equal | proportional",
      "shares": [ { "member_id": "…", "amount": 400 } ]
    }
  ]
}
```

Правила:
- Суммы — целые в минорных единицах валюты расхода.
- Простой расход «поровну» — один item с распределёнными долями.
- `extras` — дополнительные начисления к чеку (чаевые, сбор, скидка со знаком минус). В событие уходит результат распределения, не только правило.
- Инвариант: `sum(payers) == sum(items.shares) + sum(extras.shares)`.
- `wallet_id` в `payers[]` и `shares[]` — опциональное поле, зарезервировано под выбор кошелька на операцию. v1 не пишет.
- `date` — локальная дата строкой `YYYY-MM-DD`, без таймзоны. Редактируется пользователем, по умолчанию сегодня.

#### Версионирование

- `schema_version` на каждом событии.
- Клиент, встретивший неизвестный `type` или более новую версию, **игнорирует событие, не падает**, и показывает баннер «обновите приложение».
- Расширение payload — только добавлением опциональных полей.

### 4.3 Проекции

Все проекции строятся из журнала, хранятся в Room как кэш и могут быть перестроены с нуля.

| Проекция | Из чего | Что содержит |
|---|---|---|
| **Настройки** | `GroupCreated`, `GroupSettingChanged` | Текущее значение каждого ключа по LWW. |
| **Участники** | `Member*`, `Wallet*` | Список, статус (плейсхолдер / заклеймлен / архивирован), профиль, кошелёк. |
| **Расходы и переводы** | `Expense*`, `Settlement*` | Текущая версия каждой сущности по LWW. |
| **Лента** | все события | Главный экран, правила отображения — §5.6. |
| **Нетто по валютам** | расходы, переводы, кошельки | `net[wallet][currency] = заплатил − доли + получил − отправил`, свёрнуто по кошелькам. |
| **Нетто в базовой** | нетто + курсы | В масштабированных единицах, для валют с курсом. Валюты без курса — отдельно. |
| **План переводов** | нетто | Результат алгоритма упрощения. |

**Кошельки ретроактивны.** `net[wallet]` считается по текущему назначению участников в кошельки, для всей истории поездки. Назначение Марины в общий кошелёк с Митей в середине поездки сворачивает и все её прошлые доли. Это сознательное решение: «временная привязка» отклонена, иначе проекция зависела бы от порядка событий кошелька относительно расходов.

### 4.4 Правила расчётов (часть контракта)

Эти правила обязаны совпадать на всех платформах бит в бит и покрыты golden-тестами. **Вся арифметика — целочисленная.** Плавающая точка не используется нигде в контракте.

**Минорные единицы.** Таблица ISO 4217 в приложении: RUB/USD/EUR/GEL — 2, JPY — 0, KWD — 3 и т. д.

**Округление.** Единственный режим — *half away from zero*: `0.5 → 1`, `−0.5 → −1`. Применяется только в листьях (§4.4, «Мультивалюта»), никогда внутри расчётов.

**Распределение суммы `T` по весам `w_1..w_n`** (метод наибольших остатков):
1. `W = Σ w_i`, `A = |T|`.
2. `base_i = A · w_i div W`, `rem_i = A · w_i mod W`.
3. `r = A − Σ base_i` — столько участников получают `+1`: с наибольшим `rem_i`; при равенстве — по порядку в списке долей.
4. Если `T < 0` — все доли отрицаются.

Веса по режимам ввода:

| Режим | Веса |
|---|---|
| Поровну (по умолчанию) | все `1` |
| Точные суммы | распределения нет, суммы вводятся вручную, инвариант проверяется |
| Веса | целые, как введены |
| Проценты | базисные пункты (`12.5 % → 1250`), `Σ = 10000` |

Хранится результат распределения, не режим.

**Extras:** `equal` — сумма распределяется по правилу выше между всеми участниками расхода (у кого есть доля хоть в одном item), веса `1`; `proportional` — веса равны суммам долей участника по items.

**Мультивалюта.**
- Курс `rate.<CUR>` хранится как **масштабированных единиц базовой за одну минорную единицу `CUR`**, то есть минорных базовой × 1e6. Пример: база RUB, 1 GEL = 30.50 RUB → 1 тетри = 0.305 копейки → `rate.GEL = 305000`. UI вводит и показывает «30.50 ₽ за 1 GEL», пересчёт в формат хранения — на клиенте при создании события.
- Нетто в базовой в масштабированных единицах: `net_base[w] = Σ_c net[w][c] · rate[c]`. **Без округления.** Сумма по всем кошелькам равна нулю точно: `Σ_w net_base[w] = Σ_c rate[c] · Σ_w net[w][c] = 0`.
- Валюта без курса не объединяется: её нетто и план переводов показываются отдельно в её минорных единицах, с предложением подгрузить или ввести курс.
- Перевод записывается в той валюте, в которой реально ушли деньги; проекция сводит через курсы.
- `closed = true` замораживает курсы (UI) — защита от «ожившего» долга в 40 рублей через месяц после расчёта.

**Округление в листьях.** Масштабированные единицы доходят до трёх мест и только там округляются:
1. **Показ баланса**: `round(net_base / 1e6)`.
2. **Сумма перевода в плане**: `round(amount / 1e6)`; переводы, округлившиеся в ноль, из плана исключаются.
3. **Признак «рассчитались»**: `|net_base| < 1e6`, то есть меньше одной минорной единицы. После реального перевода на 4 200,00 ₽ у участника остаётся хвост в доли копейки — он видит ноль.

**План переводов (упрощение долгов, всегда включено).** По каждой расчётной валюте (базовая — в масштабированных единицах, каждая без курса — в своих минорных):
1. Кошельки с нетто > 0 — кредиторы, < 0 — должники.
2. Отсортировать обе группы по убыванию `|нетто|`, при равенстве — по `wallet_id`.
3. Перевод от крупнейшего должника крупнейшему кредитору на `min(|долг|, |кредит|)`, уменьшить обоих, обнулившегося убрать.
4. Повторять до пустоты.

Гарантии: ≤ n−1 переводов; детерминизм на всех устройствах; в масштабированных единицах план применяется к нетто точно в ноль; после округления сумм переводов остаток по каждому кошельку меньше одной минорной единицы. Переводы внутри одного кошелька невозможны.

### 4.5 Синхронизация

**Протокол** (`/v1`, JSON):

| Метод | Кто | Назначение |
|---|---|---|
| `GET /server/info` | все | Версия сервера, версия протокола. Без авторизации. |
| `POST /devices` | хост-ссылка | Тело: `device_id, device_pubkey, host_token`. Ответ: device token с правами хоста. |
| `POST /invites/{token}/join` | инвайт | Тело: `device_id, device_pubkey, member_id \| new_member_name`. Ответ: `group_id`, device token, meta. |
| `POST /groups` | любой device token | Создать группу на сервере, залить начальный журнал. |
| `POST /groups/{gid}/events` | участник группы | Пачка событий. Идемпотентно по `event_id`. Ответ: `[{event_id, server_seq}]`. |
| `GET /groups/{gid}/events?after={seq}&limit=500` | участник группы | События после курсора. |
| `GET /groups/{gid}/stream` | участник группы | WebSocket: новые события в реальном времени, пока приложение на экране. |
| `POST /groups/{gid}/invites` | участник группы | `{ttl, max_uses}`. |
| `DELETE /invites/{token}` | участник группы | |
| `GET /groups` | хост | Список групп на сервере (id, размер журнала, дата последнего события; имён нет — сервер их не знает). |

**Авторизация:** device token в `Authorization: Bearer`. Токен привязан к устройству и к набору групп, в которые оно вошло. Создать группу может любое устройство, зарегистрированное на сервере, — хост не нужен.

**Цикл синка на клиенте** (на группу):
1. Отправить все локальные события с `server_seq == null`.
2. Запросить события `after = last_server_seq`, применить, обновить курсор.
3. Пересчитать затронутые проекции.

Триггеры: открытие приложения, создание события, WorkManager раз в 15 минут, WebSocket-уведомление, (позже) push-poke.

**Конфликты.** Единственная модель — **last-writer-wins по HLC** на уровне сущности. Сущности: расход, перевод, участник, кошелёк, пара `(группа, ключ настройки)`. Проигравшая версия остаётся в журнале и видна в истории правок. Правило применяется единообразно, включая пару «удалил / отредактировал».

**HLC.** Спецификация, обязательная для всех платформ:
- Состояние устройства: `(phys_ms: u48, logical: u16)`.
- Выпуск локального события: `now = wall_clock_ms()`. Если `now > phys_ms` — `phys_ms = now, logical = 0`; иначе `logical += 1`.
- Приём чужого события `(p, l)`: `now = wall_clock_ms()`; `m = max(phys_ms, p, now)`; если `m == phys_ms == p` — `logical = max(logical, l) + 1`; иначе если `m == phys_ms` — `logical += 1`; иначе если `m == p` — `logical = l + 1`; иначе `logical = 0`; `phys_ms = m`.
- Сериализация: `{phys_ms:012x}-{logical:04x}-{device_short}`, где `device_short` — первые 8 hex-символов `device_id`. Строка нижним регистром, фиксированной длины, поэтому лексикографический порядок совпадает с числовым.
- Сравнение при LWW: сначала строка HLC целиком (включая `device_short`), при полном совпадении — `event_id`. Ничья невозможна.
- Защита от сбитых часов (событие из далёкого будущего перетягивает часы всей группы) — см. §9, открытый вопрос.

### 4.6 Идентичность и доступ

Три независимых механизма, которые нельзя схлопывать:

1. **Кто ты** — ключевая пара Ed25519 на устройстве, генерируется при первом запуске. Аккаунтов, email, паролей нет.
2. **Можно ли тебе в группу** — invite-токен с настраиваемыми TTL и числом использований.
3. **Что провода не слушают** — TLS с пиннингом (§4.7).

**Подпись событий.** Клиент подписывает каждое событие приватным ключом: Ed25519 над каноническим JSON (RFC 8785, JCS) конверта без `signature` и `server_seq`. В v1 ни сервер, ни клиенты подпись не проверяют — она только хранится. Смысл: события неизменяемы, дописать подписи к старым потом невозможно; на клиенте это десять строк.

**Клейм.** При входе по ссылке пользователь видит список незанятых плейсхолдеров группы и «Новый участник». Выбор → `MemberClaimed` + отправка своего профиля. Отвязать (`MemberUnclaimed`) может любой участник — это покрывает потерю телефона.

**Хост.** Скрипт установки печатает хост-ссылку `splinter://host?u=<host:port>&f=<sha256-b64url>&t=<host_token>`. Приложение по ней регистрирует устройство хостом: видит список групп сервера, может подключить любую и залить в неё журнал. Внутри поездки хост ничем не отличается. Обновление сервера — тем же скриптом на VPS (этап 2); из приложения по SSH — этап 3.

### 4.7 Транспортная безопасность

- При установке сервер генерирует self-signed сертификат (10 лет). Отпечаток SPKI (SHA-256) — «ключ с деплоя».
- Хост получает отпечаток из вывода скрипта в своей SSH-сессии → доверие бутстрапится через уже аутентифицированный канал.
- Отпечаток входит в invite-ссылку/QR. Клиент пинит его (`OkHttp CertificatePinner`); несовпадение = отказ.
- Домен и Let's Encrypt не нужны. Cleartext HTTP запрещён.
- Ротация сертификата — редкое хостовое действие, все получают новую ссылку.

**Формат invite-ссылки:** `splinter://join?u=<host:port>&f=<sha256-b64url>&t=<token>` — та же строка в QR.

### 4.8 Сервер

**Стек:** Python 3.12, FastAPI. Один или два контейнера в `docker compose` — зависит от выбора БД.

**Требования к хранилищу:** append-only таблица событий с монотонным `server_seq` внутри группы; уникальность `event_id`; выборка по `(group_id, server_seq > cursor)`; таблицы `groups`, `devices` (id, pubkey, токены — без имён), `invites`. Оповещение WebSocket-подписчиков о вставке.

**БД — открытый вопрос (§9).** Два кандидата:
- **SQLite** в том же контейнере: один процесс, оповещение в памяти, бэкап = копия файла, миграций почти нет. Достаточно для нагрузки «компания друзей».
- **PostgreSQL 16** отдельным контейнером: `NOTIFY` → воркер рассылки, `pg_dump` кроном. Больше движущихся частей, зато привычнее.

Аргумент за простоту: полный журнал есть на каждом клиенте, восстановление = залить журнал на новый сервер, поэтому долговечность БД — не критичное требование.

**Установка (`deploy/install.sh`, этап 2):** запускается на VPS root'ом или через sudo.
1. `/etc/os-release` → дистрибутив. **Полная автоматика: Ubuntu LTS, Debian.** Остальное — путь «Docker уже установлен», иначе понятная ошибка.
2. Если `docker` нет — `get.docker.com`. Проверить compose-plugin.
3. Открыть порт: `ufw` на Ubuntu/Debian; иначе сообщить.
4. Записать `/opt/splinter/{docker-compose.yml, .env}`, сгенерировать сертификат и хост-токен, `docker compose up -d`. Образы — с GHCR (зеркало под российские VPS), `amd64` + `arm64`.
5. Напечатать хост-ссылку и QR (`qrencode -t ANSI`, если есть).

Команды того же скрипта: `install.sh update` (`compose pull && up -d`, миграции на старте), `install.sh status`, `install.sh host-link` (напечатать ссылку ещё раз), `install.sh rotate-cert`. Файлы — в `/opt/splinter/`, контейнеры помечены `label=splinter`. Хост-креды в приложении не хранятся.

**Этап 3 (позже):** те же шаги из приложения по SSH (sshj), подключение к существующему серверу по `docker ps --filter label=splinter`. Скрипт остаётся источником истины, приложение его вызывает.

### 4.9 Пуши (опционально)

Чтобы отправить FCM-пуш, серверу нужен service-account ключ Firebase-проекта, к которому привязан APK. Раздать его каждому self-hosted серверу нельзя, а сама библиотека FCM проприетарна и закрывает дорогу в основной репозиторий F-Droid.

**v1:** без пушей. WorkManager раз в 15 минут + синк при открытии + WebSocket на переднем плане.

**Позже:** пуш — только *poke* `{server, group_id}` без содержимого, приложение синкается само. Транспорт — **UnifiedPush**: без Google, совместим с F-Droid, сервер шлёт poke на URL, который выдал дистрибьютор на телефоне. На устройствах без дистрибьютора — polling.

### 4.10 Клиент

**Стек:** Kotlin, Jetpack Compose, Room, Hilt, OkHttp, kotlinx.serialization, WorkManager, ZXing (QR).

**Слои:**
- `contract` — модели событий, правила расчётов, алгоритмы проекций. Чистый Kotlin без Android-зависимостей, покрыт golden-тестами. Держится чистым сознательно: это делает переход на Kotlin Multiplatform для iOS дешёвым, и Swift-переписывание расчётов не понадобится.
- `data` — Room (журнал + кэш проекций), sync-клиент, ключи (Android Keystore).
- `ui` — Compose.

**Room:**

| Таблица | Назначение |
|---|---|
| `servers` | `url, fingerprint, device_token, is_host` |
| `groups` | `group_id, server_id?, my_member_id` |
| `events` | Сырой журнал: `event_id, group_id, hlc, type, payload, server_seq?` |
| `sync_state` | `group_id, last_server_seq` |
| `settings`, `members`, `wallets`, `expenses`, `settlements` | Кэш проекций, перестраиваемый. |
| `profile` | Локальный профиль устройства: имя, реквизиты, ключевая пара (Keystore). |

**Аватарки** — детерминированно из `member_id` (цвет + инициалы), по одному алгоритму на всех устройствах, в событиях не хранятся. Кастомная аватарка — позже, как блоб в `MemberProfileUpdated` с лимитом payload 64 КБ.

**Дип-линки:** `splinter://join?…` (инвайт), `splinter://host?…` (хост-ссылка), `splinter://g/{group_id}/e/{expense_id}` (расход). Без https app links — домена нет.

### 4.11 Импорт из Splitwise

CSV-экспорт Splitwise даёт по каждому расходу дату, описание, сумму, валюту и нетто-изменение баланса каждого участника. Импортёр: участники → плейсхолдеры (с маппингом на существующих), расход → `ExpenseAdded` с одним item. Для расходов с одним плательщиком доли восстанавливаются точно (`share_i = −net_i`, плательщик — `cost − sum(others)`); для нескольких плательщиков — best-effort с пометкой в описании.

## 5. Логика работы приложения

### 5.1 Первый запуск

1. Генерируется ключевая пара Ed25519 и `device_id`, кладутся в Keystore.
2. Экран профиля: имя (обязательно), реквизиты для перевода (опционально, свободный текст: «СБП +7…», «IBAN …»). Профиль хранится локально и уезжает в каждую группу при клейме.
3. Дальше — список поездок (пустой) с двумя действиями: «Новая поездка» и «Войти по ссылке». Если приложение открыто по дип-линку — сразу соответствующий сценарий.

### 5.2 Навигация

```
Поездки ──► Поездка ──┬─ Лента (главный экран)
                      ├─ Балансы
                      ├─ Участники
                      └─ Настройки
                      [FAB: + Расход]   [меню: Записать перевод · Поделиться · Экспорт]
```

Поездка открывается на Ленте. Балансы и Участники — вкладки. Настройки — из меню.

### 5.3 Поездка

**Создание:** название, базовая валюта (по умолчанию — из последней поездки, иначе RUB). Приложение добавляет создателя как участника и заклеймливает его. → `GroupCreated`, `MemberAdded`, `MemberClaimed`, `MemberProfileUpdated`.

**Настройки:** название, базовая валюта, таблица курсов, «Закрыть поездку» / «Открыть заново». Каждое поле — отдельное `GroupSettingChanged`.

**Курсы:** таблица «валюта → курс к базовой» для всех валют, встречающихся в журнале. Ввод вручную или «Подгрузить» (источник — §9). Обновление уже заданного курса — с предупреждением «балансы могут измениться». Каждая валюта — своё событие `rate.<CUR>`.

**Закрытие:** `closed = true`. UI прячет «+ Расход», блокирует правку курсов и состава, поездка уходит в раздел «Архив». «Открыть заново» — с предупреждением, `closed = false`.

**Поделиться:** если поездка на сервере — экран инвайта: TTL (по умолчанию 7 дней), число использований (по умолчанию 10), ссылка + QR. Если не на сервере — предложение подключить сервер.

**Экспорт/импорт:** JSON-файл с полным журналом группы (`{version, events: [...]}`). Импорт создаёт поездку локально из журнала, идемпотентен по `event_id` — импорт в существующую поездку просто добавляет недостающие события.

### 5.4 Расход

Форма создания, сверху вниз:

1. **Сумма** — поле-калькулятор: `120+80*2` считается на лету. Валюта рядом, по умолчанию — из последнего расхода этой поездки.
2. **Описание.**
3. **Кто платил** — по умолчанию «я». Тап — выбор одного или нескольких с суммами; суммы нескольких плательщиков должны сходиться к итогу.
4. **Как делить** — переключатель режимов:
   - *Поровну* (по умолчанию): чекбоксы участников, все включены.
   - *Точные суммы*: поле у каждого, остаток показан.
   - *Веса*: целое у каждого.
   - *Проценты*: с одним знаком после запятой.
   - *По позициям*: список позиций «название, сумма, кто», каждая — поровну между выбранными; ниже — extras «название, сумма (можно отрицательную), equal/proportional».
5. **Дата** — сегодня, тап меняет.
6. **Сохранить** → `ExpenseAdded` с посчитанными долями. Внизу формы всегда виден результат: «Айрат 40.00 · Никита 40.00 · …», чтобы остаток округления был виден до сохранения.

Правка открывает ту же форму, заполненную из текущей версии → `ExpenseUpdated` с полным payload. Удаление — с подтверждением → `ExpenseDeleted`.

Расход в закрытой поездке открывается только на чтение.

### 5.5 Балансы

Экран из трёх уровней, сверху вниз:

1. **Мой итог.** «Вы должны 4 200 ₽» / «Вам должны …» / «Вы рассчитались». По базовой валюте — округлённое `net_base`; по каждой валюте без курса — отдельная строка. Если в поездке есть валюты без курса — баннер «GEL, USD без курса: задать».
2. **План переводов.** Строки «кто → кому сумма», мои — наверху. У моей строки-долга кнопка **«Погасить»**: форма перевода, предзаполненная от/кому/сумма/валюта, ниже — реквизиты получателя из его профиля. Подтверждение → `SettlementRecorded`. У чужих строк — просто информация. Сумма перевода округлена в лист; строки, округлившиеся в ноль, не показываются.
3. **Нетто по кошелькам.** Список кошельков с нетто. Общий кошелёк раскрывается на участников. Участник раскрывается на список расходов и переводов, из которых сложилось: «Ужин −800 · Такси −200 · Перевод Мите +1 000». Это ответ на «из чего сложилось».

**«Записать перевод»** из меню — та же форма, пустая. Частичное погашение и переплата легальны: это просто перевод, проекция пересчитает.

Расчётные валюты (базовая + каждая без курса) показываются отдельными блоками, каждый со своим планом.

### 5.6 Лента

Правила отображения — часть контракта, потому что от них зависит, что пользователь считает «порядком событий».

- **Что показывается строкой:** расходы, переводы. Порядок — по `date` (убывание), внутри одной даты — по HLC (убывание). Ключ сортировки берётся из текущей версии сущности.
- **Правки:** строка расхода/перевода показывает текущую версию. Тап раскрывает историю версий по HLC, каждая — как дифф с предыдущей: «Денис изменил: участники −Валя; сумма 250 → 240». Удалённая сущность — строка «удалено» серым, с историей.
- **Служебные события** (`Member*`, `Wallet*`, `GroupSettingChanged`) — свёрнуты в одну строку «3 служебных события» между датами, раскрываются фильтром. Подряд идущие `GroupSettingChanged` одного устройства в одном синке — одна строка: «Никита обновил курсы GEL, USD».
- **Неизвестные события** — не показываются, но считаются: баннер «2 события не распознаны — обновите приложение».
- **Синк:** индикатор наверху: «3 события не отправлены» / «синхронизировано» / «сервер недоступен». Тап — принудительный синк.

### 5.7 Участники

Список: аватарка, имя, статус (плейсхолдер / привязан / архивирован), кошелёк, реквизиты. Действия:
- «Добавить участника» → `MemberAdded`.
- На участнике: «Отвязать устройство» (если привязан), «Архивировать» (только при `|net_base| < 1e6` во всех валютах; иначе «сначала закройте долг»), «Кошелёк: личный / …».
- «Создать общий кошелёк» → `WalletCreated`, потом назначение участников → `MemberWalletAssigned`. Предупреждение при назначении: «действует на всю поездку».
- «Выйти из поездки» на себе → `MemberUnclaimed`, поездка остаётся локально в режиме «только чтение, не синкается» до удаления пользователем.

### 5.8 Вход по ссылке

1. Открыт `splinter://join?…`. Приложение проверяет отпечаток при первом подключении к серверу, запоминает сервер.
2. `GET /groups/{gid}` через инвайт-токен → название и список незанятых плейсхолдеров.
3. Экран «Поездка Грузия. Кто ты?» — плейсхолдеры + «Новый участник».
4. Выбор → `POST /invites/{token}/join`, device token сохранён, журнал скачан, эмитятся `MemberClaimed` (+ `MemberAdded` для нового) и `MemberProfileUpdated`.
5. Если у устройства уже есть участник в этой группе — ссылка просто открывает поездку.

### 5.9 Сервер и хост

- **«Подключить сервер»** в списке поездок → вставить/сканировать хост-ссылку → `POST /devices` → сервер в списке с пометкой «хост».
- **Хост видит** список групп сервера (без имён — только id, размер, дата), может «Подключить» группу: скачать журнал, затем клеймить себя. Локальную поездку можно «Отправить на сервер»: `POST /groups` с полным журналом.
- **Любой участник** поездки на сервере может создавать инвайты и новые группы на этом сервере.
- **Обновление сервера** — на VPS: `install.sh update`. Приложение при `GET /server/info` с несовместимой версией протокола показывает: «сервер 0.4, нужен ≥ 0.6, обновите на VPS».

### 5.10 Синхронизация с точки зрения пользователя

- Создал событие → оно сразу в проекциях, помечено «не отправлено» → уходит при ближайшем синке.
- Пришло чужое → проекции пересчитаны, лента обновилась, при открытом экране — мгновенно (WebSocket).
- Конфликт — не диалог. Проигравшая версия видна в истории строки, победившая — в ленте. Пользователь правит ещё раз, если не согласен.
- Офлайн неделю — ничего не ломается: при первом синке всё уходит и приходит, HLC расставляет порядок.

## 6. Фичи

### v1 — этап 1, офлайн, по инкрементам

Каждый инкремент — законченная вещь, которой можно пользоваться, со своей golden-фикстурой.

| # | Инкремент | Что входит |
|---|---|---|
| 1a | **Ядро** | Поездка, плейсхолдеры, расход «поровну» с одним плательщиком, переводы («Погасить» и «Записать перевод»), балансы с планом, лента. Одна валюта. Этого хватает на поездку с одним «бухгалтером». |
| 1b | **Режимы ввода** | Точные суммы, веса, проценты; несколько плательщиков; редактируемая дата; калькулятор в сумме; дефолты из последней операции. |
| 1c | **Позиции и extras** | Режим «по позициям», extras equal/proportional со знаком. |

| 1e | **Мультивалюта** | Валюта на расход, курсы вручную, конвертация в базовую, валюты без курса отдельно, подгрузка курсов из интернета. |
| 1f | **Жизненный цикл** | Архивирование участника, закрытие/открытие поездки, экспорт/импорт JSON, дип-линк на расход, раскрытие «из чего сложилось». |

### v1 — этап 2, сервер

## 10. Юзер-сценарии

Компания: **Митя** (хост), **Марина** (общий кошелёк с Митей), **Айрат**, **Валя**, **Никита**, **Денис**. Поездка «Грузия», базовая валюта — рубль.

### С1. Первая поездка без сервера *(1a)*
Митя создаёт «Грузия», базовая валюта RUB. Добавляет плейсхолдеры: Марина, Айрат, Валя, Никита, Денис; себя приложение добавило само. Вбивает первый расход: «Такси из аэропорта», 2 400 ₽, платил Митя, поровну на всех. Лента показывает одну строку, балансы — пять должников Мите по 400 ₽. Сервера нет.

### С2. Чек по позициям с доп. начислениями *(1c)*
Ужин. Марина вводит позиции: хинкали 80 GEL — Айрат и Никита; вино 120 GEL — все, кроме Марины; чача 30 GEL — Митя. Добавляет extra «сервис 10 %» = 23 GEL пропорционально, скидка по акции −20 GEL пропорционально. Платила Марина. Внизу формы до сохранения видно: доли посчитаны, остаток округления в 1 тетри ушёл первому в списке. Одно событие `ExpenseAdded`.

### С3. Балансы и «Погасить» *(1a)*
Через неделю Айрат открывает «Балансы»: «Вы должны 4 200 ₽». План: «Айрат → Митя & Марина 4 200 ₽» — хотя часть ужинов оплачивала Валя, упрощение свело всё к одному переводу. Айрат раскрывает строку, видит расходы, из которых сложилась сумма. Нажимает «Погасить»: форма с предзаполненными от/кому/сумма, ниже — реквизиты Мити для СБП. Переводит в банке, подтверждает. `SettlementRecorded`. В масштабированных единицах у Айрата остался хвост в 0.3 копейки от конвертации; экран показывает «Вы рассчитались».

### С4. Произвольный перевод *(1a)*
Никита занял у Дениса 3 000 ₽ наличными вне всяких чеков. Денис нажимает «Записать перевод», выбирает Никита → Денис… останавливается: деньги шли от Дениса к Никите. Записывает Денис → Никита 3 000 ₽. У Никиты появился долг Денису, которого не было в расходах. Общая касса работает так же: все скидываются Мите переводами, он платит из этого.

### С5. Общий кошелёк *(1d)*
Марина создаёт кошелёк «Митя & Марина» и назначает обоих; приложение предупреждает, что это действует на всю поездку. В расходе на шестерых у Мити и Марины по 1/6 каждому. На экране балансов — одна строка «Митя & Марина», нетто 1/3, раскрывается на двоих. План переводов никогда не предлагает перевод между ними. Кто из двоих платил картой — не важно.

### С6. Установка сервера *(этап 2)*
Митя купил VPS на Ubuntu. Заходит по SSH, запускает `curl -fsSL …/install.sh | sudo bash`. Скрипт: Ubuntu 24.04, Docker нет, ставит, открывает порт, поднимает compose, печатает хост-ссылку и QR. Митя сканирует QR приложением — устройство зарегистрировано хостом. Выбирает «Грузия» → «Отправить на сервер» → журнал уезжает. «Поделиться» → ссылка и QR: TTL 7 дней, 10 регистраций.

### С7. Вход по ссылке *(этап 2)*
Валя открывает ссылку — приложения нет, попадает в GitHub Releases, ставит APK, открывает ссылку снова. «Поездка Грузия. Кто ты? Марина · Айрат · Валя · Никита · Денис · Новый участник». Выбирает Валю, приложение отправляет её профиль и тянет журнал. Денис пришёл позже, чем ожидалось, и его никто не завёл — он выбирает «Новый участник», вводит имя, `MemberAdded` + `MemberClaimed`.

### С8. Офлайн параллельно *(этап 2)*
В горах без связи Никита записывает бензин, Айрат — обед. Вечером в отеле оба синкаются: каждый отправляет своё, получает чужое, HLC расставляет порядок, балансы у всех совпадают. Конфликтов нет — это разные сущности.

### С9. Конфликт правки *(этап 2)*
Митя и Денис офлайн правят один ужин: Митя меняет сумму 240 → 250, Денис убирает Валю из участников. После синка побеждает событие с бо́льшим HLC (Дениса): в ленте текущая версия — 240 без Вали. Митя раскрывает историю: «Денис изменил: участники −Валя; сумма 250 → 240» — и правит ещё раз, если нужно. Обе версии в истории.

### С10. Курсы и мультивалюта *(1e)*
Часть расходов в GEL, перелёты в RUB, один ужин в USD. Балансы показывают: «GEL и USD — без курса» отдельными планами. Валя нажимает «Подгрузить курсы» — приложение тянет GEL и USD на сегодня, два события `GroupSettingChanged` (`rate.GEL`, `rate.USD`), план сливается в один в рублях. Через две недели Никита нажимает «Обновить курсы», видит предупреждение «балансы могут измениться», соглашается — у всех сдвинулось на десятки рублей, и это видно в ленте одной строкой «Никита обновил курсы GEL, USD».

### С11. Потеря телефона *(этап 2)*
Никита утопил телефон. Новый телефон, ссылка от Мити, в списке «Никита» помечен как занятый. Любой участник (Митя) нажимает «Отвязать Никиту» → `MemberUnclaimed`. Никита выбирает себя, `MemberClaimed`, все его долги на месте, история — тоже.

### С12. Переустановка приложения и обновление сервера *(этап 2)*
Митя снёс приложение. Ставит заново, «Подключить сервер»: заходит на VPS, `install.sh host-link`, сканирует QR. Приложение видит сервер 0.4 против своего 0.6, говорит «обновите сервер». Митя запускает `install.sh update`, миграции на старте. Приложение показывает «Грузия» и «Байкал», Митя подключает «Грузию», тянет журнал, заклеймливает себя.

### С13. Две поездки на одном сервере *(этап 2)*
Валя создаёт «Байкал» локально и сама отправляет её на сервер — она уже зарегистрирована там через «Грузию», хост не нужен. Делится ссылкой. В «Байкале» нет Мити. Митя как хост видит на сервере обе группы, подключён к одной. Балансы «Грузии» и «Байкала» не пересекаются.

### С14. Выход и архивирование *(1f, этап 2)*
Денис вернулся домой, долги закрыл, «Выйти из поездки» → устройство отвязано, плейсхолдер и история остались. Марина хочет убрать «Гостя», у которого висит 200 ₽, — приложение говорит «сначала закройте долг». После перевода «Гость» архивируется и исчезает из выбора участников, но остаётся в истории.

### С15. Возврат в магазине *(1a)*
Айрат вернул куртку, за которую платил на всех. Удаляет расход — `ExpenseDeleted`, балансы пересчитались. Вернули половину — правит сумму.

### С16. Без пушей и без Google *(этап 2)*
У Никиты Huawei без Google-сервисов. Он открывает приложение — синк при старте. Пока закрыто — WorkManager раз в 15 минут. Ничего не теряется, просто узнаёт не мгновенно.

### С17. Импорт из Splitwise *(1g)*
Валя выгружает CSV из старой группы Splitwise, открывает в Splinter. Приложение показывает найденных участников и предлагает сопоставить с плейсхолдерами; расходы ложатся в новую поездку как `ExpenseAdded` с пометкой «импорт из Splitwise». Балансы совпадают с тем, что показывал Splitwise.

### С18. Закрытие и повторное открытие *(1f)*
Все рассчитались. Митя нажимает «Закрыть поездку» → `closed = true`. Курсы и состав заморожены, новые расходы нельзя, поездка уходит в архив. Через месяц Валя вспоминает забытый чек: «Открыть заново» с предупреждением → `closed = false`, добавляет расход, закрывает снова. В ленте оба переключения видны.

### С19. Конфликт настроек *(этап 2)*
Офлайн: Валя задаёт курс GEL, Никита в тот же час — курс USD, а Митя переименовывает поездку в «Грузия 2026». После синка выжили все три изменения: LWW идёт по паре `(группа, ключ)`, а не по «настройкам целиком».

## 11. Инварианты и golden-тесты

Фикстуры `contract/golden/<case>/{log.json, expected.json}`, прогоняются на каждой платформе. `expected.json` содержит настройки, участников, нетто по валютам, нетто в базовой (масштабированное), план переводов (масштабированный и округлённый) и порядок ленты.

1. Сумма нетто по каждой валюте равна нулю на любом журнале.
2. Сумма `net_base` по кошелькам равна нулю точно (в масштабированных единицах) на любом журнале с любыми курсами.
3. План переводов в масштабированных единицах, применённый к `net_base`, даёт нули по всем кошелькам; после округления сумм переводов остаток по каждому кошельку `< 1e6`.
4. Один и тот же набор событий в любом порядке прихода даёт идентичные проекции, план и порядок ленты.
5. Общий кошелёк из двух участников с долями 1/6 + 1/6 → нетто 1/3 в плане; перевод между ними не генерируется; назначение в кошелёк после расходов даёт тот же результат, что до.
6. Распределение 100 на 3 поровну → `34, 33, 33` в порядке участников; 1000 JPY на 3 → `334, 333, 333`; 1.000 KWD на 3 → `334, 333, 333` в фильсах; −100 на 3 → `−34, −33, −33`; 100 по весам 1:2 → `33, 67`.
7. Extras `equal` и `proportional` дают ожидаемые доли на эталонном чеке из С2.
8. Обновление курсов меняет `net_base`, но не нетто по валютам.
9. LWW: при двух `ExpenseUpdated` с разным HLC в проекции — версия с бо́льшим HLC независимо от порядка прихода; при одинаковом HLC — по `event_id`.
10. LWW по настройкам: `rate.GEL`, `rate.USD` и `name` из трёх источников (С19) выживают все.
11. HLC: последовательность «выпуск, приём из будущего, выпуск» даёт монотонно возрастающие строки; сериализация лексикографически упорядочена.
12. Неизвестный тип события пропускается, остальные применяются; счётчик пропущенных равен ожидаемому.
13. Импорт эталонного Splitwise-CSV даёт балансы, совпадающие с эталоном.
14. Экспорт → импорт журнала даёт идентичные проекции.

## Изменения v0.1 → v0.2

- **Формат:** дизайн-документ → предложение; добавлены §0 «Проблема и решение» и §5 «Логика работы приложения».
- **Деплой:** скрипт `deploy/install.sh` и хост-ссылка — этап 2; SSH из приложения — этап 3. Хост-креды в приложении не хранятся.
- **Репозиторий:** три репо → монорепо с явным разделением; генерация Python-моделей убрана, сервер валидирует только конверт.
- **БД сервера:** PostgreSQL → открытый вопрос, SQLite как кандидат.
- **Настройки:** `GroupSettingsChanged{name?, base_currency?, rates?}` и `GroupClosed` → `GroupSettingChanged{key, value}` с LWW на паре `(группа, ключ)`; курсы — по ключам `rate.<CUR>`; закрытие — ключ `closed`, обратимо.
- **Расчёты:** плавающая точка убрана, распределение — целочисленный метод наибольших остатков; режим округления зафиксирован (half away from zero); нетто в базовой считается без округления в масштабированных единицах, округление только в листьях (показ, сумма перевода, признак «рассчитались»); формат хранения курса — минорные базовой за минорную валюты × 1e6.
- **Инвариант 2** переформулирован: точный ноль в масштабированных единицах, остаток после округления переводов < 1 минорной.
- **HLC:** спецификация выпуска, приёма, сериализации и сравнения; защита от сбитых часов — в открытые вопросы.
- **Кошельки:** ретроактивность записана явно.
- **Хост:** создавать группы на сервере может любое устройство; хост — только список групп и обновление.
- **Подпись событий:** поле в конверте, пишется, не проверяется (предложение).
- **Пуши:** UnifiedPush вместо FCM-relay из-за F-Droid.
- **Распространение:** GitHub Releases → IzzyOnDroid → F-Droid; лицензия блокирует первый публичный коммит.
- **Этап 1** разбит на инкременты 1a–1g.
- **Сценарии:** С6, С12, С13 переписаны под скрипт; С3 — хвост округления; С18 — повторное открытие; добавлен С19.
